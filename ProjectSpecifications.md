# Project Specifications — Dopamine Feed Online

## 1. Project Overview

**Project name:** Dopamine Feed Online  
**Working product name:** Dopamine Feed

Dopamine Feed is a continuously evolving, entirely synthetic social-media feed.

The user experience should resemble the compelling scrolling experience of products such as Reddit, X/Twitter, Threads, Hacker News, and similar feeds, but **all accounts, posts, discussions, reactions, events, communities, and storylines are synthetic and generated by AI**.

The application should feel less like a collection of unrelated AI-generated posts and more like a small fictional internet that continues to evolve over time.

The primary V1 question is:

> Is scrolling through a persistent, entirely synthetic internet entertaining enough that people want to keep scrolling?

V1 should optimize for answering that question with the smallest reasonable architecture.

---

# 2. Core Principles

## 2.1 Static-first architecture

V1 must not require an application backend, database, authentication system, or server-side runtime.

The application consists of:

1. a static frontend;
2. static JSON feed data;
3. a generator that runs periodically in GitHub Actions;
4. persistent synthetic-world state stored in the repository.

GitHub Pages hosts the application.

The browser reads generated JSON files directly.

---

## 2.2 Generate offline, consume online

AI generation must **never happen in the browser**.

Generation occurs only inside GitHub Actions.

The frontend must not contain or receive the OpenRouter API key.

The architecture is:

```text
GitHub Actions
      │
      ├── read prompts
      ├── read persistent world state
      ├── read recent feed context
      │
      ▼
OpenRouter
model: openrouter/free
      │
      ▼
validate generated response
      │
      ├── invalid → retry
      │
      └── valid
           │
           ├── update world state
           ├── write new feed batch
           ├── update manifest
           └── publish GitHub Pages
                     │
                     ▼
                Web browser
                     │
                     ▼
              static JSON feed
```

# 5. Synthetic World Model

The generator must not simply ask:

> Generate 20 random social-media posts.

That would create disconnected AI content and is explicitly not the desired product.

Instead, generation should represent **advancing a persistent synthetic world by one generation cycle**.

The world should contain persistent entities such as:

- synthetic users;
- personalities;
- interests;
- opinions;
- relationships;
- communities;
- recurring jokes;
- active arguments;
- events;
- ongoing storylines;
- previous claims or predictions;
- cultural references created inside the synthetic world;
- memories of significant previous interactions.

A generated account should continue to behave recognizably across multiple runs.

For example, someone who is habitually skeptical, overly earnest, sarcastic, argumentative, obsessed with a niche hobby, or constantly posting bad startup ideas should retain that personality.

Characters should sometimes respond to previous events or people rather than behaving as isolated content generators.

---

# 6. Synthetic Accounts

Bootstrap approximately **30–50 persistent synthetic accounts**.

The precise count may be configurable.

Each account should have structured characteristics such as:

```text
id
handle
display name
short bio
personality traits
interests
writing style
communities
behavioral tendencies
relationships
activity level
```

Internal state may additionally contain details that do not need to appear in `accounts.json`.

Accounts must be fictional.

Do not impersonate real private individuals.

Avoid generating fake posts attributed to real public figures.

Avatars in V1 should be generated locally through deterministic visual treatments such as:

- initials;
- gradients;
- geometric patterns;
- identicons.

Do not depend on an external avatar service.

---

# 7. Communities and Topics

The synthetic world should have several loose topic clusters or communities.

Examples of categories, not required literal names:

- technology;
- gaming;
- relationships;
- work;
- local/community chatter;
- entertainment;
- hobbies;
- weird internet culture;
- science;
- unpopular opinions;
- absurd humor.

The world should not feel evenly distributed across categories.

Topics can temporarily become unusually popular due to synthetic events.

---

# 8. Feed Generation

## 8.1 Frequency

Automatic generation occurs **once every three hours**.

Use a GitHub Actions scheduled workflow.

Do not schedule exactly at the top of an hour.

A suitable schedule is approximately:

```text
17 */3 * * *
```

Generation must also support manual execution using:

```text
workflow_dispatch
```

This allows a new generation cycle to be triggered from GitHub Actions at any time.

Exact execution time must not be important to application correctness.

---

## 8.2 Generation size

Default target:

**20 top-level feed items per generation cycle.**

This should be configurable rather than deeply hardcoded.

A cycle may also produce approximately **25–60 comments/replies** distributed across those items.

Not every post needs comments.

Some posts should receive substantial discussion while others receive almost none.

---

# 9. Feed Content

The feed should contain meaningful variation.

Possible item types include:

- ordinary text post;
- question;
- discussion;
- hot take;
- observation;
- personal anecdote;
- joke;
- community post;
- announcement;
- fake link-preview style post;
- reaction to another synthetic post;
- quote/repost style content.

V1 does not require AI-generated images.

Text-first is preferred.

The application should be architected so media can be added later without redesigning the feed model.

---

# 10. Content Quality Requirements

Generated content must avoid the stereotypical feeling of an AI-generated feed.

Specifically:

### Do

- vary post length dramatically;
- allow short low-effort posts;
- include occasional imperfect grammar;
- allow different punctuation habits;
- give users distinctive writing styles;
- create recurring references;
- create callbacks to older posts;
- allow disagreements;
- allow mild profanity where natural;
- include mundane posts;
- include niche posts;
- include jokes that do not explain themselves;
- let some conversations go nowhere;
- let some characters be annoying;
- let some topics become unexpectedly popular;
- let characters remember past interactions.

### Do not

- make every post insightful;
- make everyone unusually articulate;
- end everything with a question;
- overuse headings or bullet points;
- make every character sound like ChatGPT;
- make every discussion polite and balanced;
- produce generic inspirational content repeatedly;
- constantly explain jokes;
- make all posts approximately the same length;
- make every generation cycle independent of previous cycles.

The feed should feel messy and heterogeneous in the way real social feeds are.

---

# 11. World Continuity

Each generation cycle receives enough previous state to understand what is happening in the synthetic world.

However, prompt size must remain bounded.

Do **not** continuously append every historical post to the prompt.

Instead maintain a compact structured world state containing things such as:

```text
active storylines
important recent events
character memories
relationships
running jokes
recent conflicts
current trends
unresolved threads
```

Old events should eventually be summarized or forgotten unless they remain important.

Suggested limits include:

- bounded active storylines;
- bounded per-character memories;
- bounded global world memories;
- only summaries of old feed batches.

The generator should deliberately prevent state from growing without limit.

---

# 12. OpenRouter Integration

Use OpenRouter for generation.

The model identifier for V1 is:

```text
openrouter/free
```

The GitHub Actions environment provides:

```text
OPENROUTER_API_KEY
```

as a GitHub Actions secret.

The API key must never:

- be committed;
- appear in generated files;
- appear in frontend JavaScript;
- be logged;
- be placed in GitHub Pages output.

Provide an `.env.example` for local development, but never commit an actual key.

Use non-streaming generation.

Where supported, request structured JSON output using JSON Schema or equivalent structured-output functionality.

Even when structured output is requested, **never trust the response without local validation**.

---

# 13. Generation Response Validation

All AI-generated data must pass runtime validation before it can modify production data.

Use Zod or an equivalent runtime schema.

Validation should check at minimum:

- valid JSON;
- expected top-level structure;
- required fields;
- enum values;
- field-length bounds;
- valid account references;
- valid parent/reply references;
- no duplicate IDs after application-side ID generation;
- reasonable post counts;
- reasonable comment counts;
- valid world-state update structure.

The model should not be responsible for generating technical metadata that application code can generate reliably.

Prefer generating in application code:

- UUIDs/IDs;
- generation timestamps;
- file names;
- schema version;
- synthetic engagement counters where appropriate;
- other deterministic metadata.

---

# 14. OpenRouter Reliability and Retry Strategy

`openrouter/free` should be treated as an unreliable external dependency.

Failure is normal and must be handled gracefully.

Implement retries for:

- network failures;
- timeouts;
- HTTP 429;
- retryable 5xx responses;
- missing completion content;
- malformed JSON;
- schema-invalid JSON;
- invalid cross-references;
- incomplete generations.

Suggested maximum:

```text
5 attempts
```

Use exponential backoff with jitter.

For example, approximately:

```text
2 sec
5 sec
10 sec
20 sec
```

between subsequent attempts.

Exact delays may differ.

If a response contains only a simple outer Markdown JSON code fence, the parser may safely remove that fence before JSON parsing.

Do not implement aggressive heuristic JSON repair.

If JSON is actually malformed, retry generation.

For schema-validation failures, a retry may include a concise explanation of why the previous output was rejected.

---

# 15. Transactional Publishing

Generation must behave transactionally.

This is important.

A failed run must **never corrupt or partially replace a previously valid feed**.

The workflow is:

```text
load current valid state
        │
        ▼
generate candidate output
        │
        ▼
validate candidate completely
        │
      invalid
        │
       retry
        │
        ▼
valid candidate
        │
        ├── construct next world state
        ├── validate resulting world state
        ├── write batch
        ├── write accounts
        └── update manifest
```

Files should only replace live files after the entire candidate generation has passed validation.

If every retry fails:

1. exit with a failed GitHub Actions run;
2. do not modify world state;
3. do not publish partial content;
4. leave the previous live site/feed untouched.

A failed generation cycle is preferable to corrupted state.

---

# 16. Batch Storage

Do not store the entire feed in one continually growing JSON file.

Use immutable batch files.

Example:

```text
public/data/
├── manifest.json
├── accounts.json
└── batches/
    ├── 20260915T031700Z-a81d.json
    ├── 20260915T061700Z-91bf.json
    └── 20260915T091700Z-f291.json
```

Once successfully published, a batch should not normally change.

---

# 17. Manifest

`manifest.json` tells the frontend which batches exist.

Conceptually:

```json
{
  "schemaVersion": 1,
  "generatedAt": "ISO_TIMESTAMP",
  "latestRunId": "RUN_ID",
  "batches": [
    {
      "id": "RUN_ID",
      "generatedAt": "ISO_TIMESTAMP",
      "file": "batches/FILENAME.json",
      "itemCount": 20
    }
  ]
}
```

Newest batches should appear first.

The manifest itself is mutable.

Batch files are immutable.

---

# 18. Data Retention

Do not allow deployed static data to grow forever.

For V1, retain approximately **14 days of feed batches** in `public/data/batches`.

Older deployed batches may be removed.

Important historical information needed for continuity should be distilled into persistent world memory before old batches disappear.

Git history may naturally retain previous generated content, but the application should not depend on Git history.

Make retention configurable.

---

# 19. Feed Schema

Exact implementation may evolve, but a top-level feed item should conceptually support:

```text
id
kind
authorId
createdAt
community/topic
title (optional)
body
referencedPostId (optional)
synthetic engagement data
comments
```

Comments should support:

```text
id
authorId
createdAt
body
parentCommentId (optional)
```

Nested conversations may be represented internally using flat parent references.

Limit deeply nested replies.

---

# 20. Synthetic Engagement Metrics

Posts may display synthetic metrics such as:

- likes/upvotes;
- replies;
- reposts/shares;
- views or similar popularity signals.

These values do not need to come directly from the LLM.

Prefer application-side generation where possible.

Metrics should feel plausible and varied rather than uniformly random.

A small number of posts should dramatically outperform the median.

Very new posts should generally have lower engagement than older posts unless deliberately marked as rapidly trending.

---

# 21. Frontend Experience

The site should immediately present a scrollable feed.

No login screen.

No onboarding wall.

No configuration step.

A visitor should be able to open the site and start scrolling.

The visual language may be inspired by modern social platforms but should not directly clone the trade dress of Reddit, X, Threads, etc.

Suggested desktop structure:

```text
          header
────────────────────────
     centered feed
     ~650–750px wide

       post card
       post card
       post card
       post card
          ...
```

Mobile should use most of the available width.

---

# 22. Feed Cards

A typical card should display:

- avatar;
- display name;
- handle;
- relative timestamp;
- community/topic where applicable;
- title where applicable;
- post body;
- synthetic engagement indicators;
- comment/reply count.

Selecting a post should make its discussion easy to inspect.

This may use:

- inline expansion;
- modal;
- drawer;
- dedicated client-side view.

Choose the simplest polished approach.

---

# 23. Infinite Scrolling

On page load:

1. fetch `manifest.json`;
2. load the newest batch;
3. display it;
4. load older batches as the user approaches the bottom.

Use `IntersectionObserver` or an equivalent browser-native mechanism.

Do not download every historical batch immediately.

Batch files are immutable and may be browser cached aggressively.

The manifest should be fetched in a way that avoids users remaining indefinitely stuck on a stale manifest.

---

# 24. Ranking

V1 does not require a sophisticated recommendation engine.

The default feed can primarily use chronological ordering with modest ranking logic.

Possible lightweight factors include:

- recency;
- synthetic engagement;
- synthetic virality score;
- thread activity.

Do not build a recommendation-service backend.

Ranking logic should remain client-side or be predetermined during generation.

---

# 25. First Run / Bootstrap

The project must work when no synthetic world exists yet.

If `world.json` contains no initialized world, perform a bootstrap process.

Bootstrap should create:

- the initial account population;
- basic communities/topics;
- initial personality and relationship state;
- initial active storylines if appropriate.

After validating bootstrap state, generate the first normal feed batch.

Bootstrap may require a separate OpenRouter request from normal feed generation.

Bootstrap output must undergo the same schema validation and retry protections as ordinary generations.

Once initialized, do not recreate the world on every run.

---

# 26. GitHub Actions

The repository should contain a workflow supporting:

### Automatic execution

Every three hours.

### Manual execution

Using:

```text
workflow_dispatch
```

### Normal deployment

Ordinary pushes to the default branch should still build/test/deploy the application without unnecessarily generating a new AI batch.

Conceptually:

```text
push
  └── test → build → deploy

schedule
  └── generate → validate → persist → test → build → deploy

workflow_dispatch
  └── generate → validate → persist → test → build → deploy
```

Generated state/data should be persisted back to the repository using the GitHub Actions token or another appropriately secure first-party mechanism.

Use minimal required workflow permissions.

Only the generation job should receive `OPENROUTER_API_KEY`.

Prevent overlapping generation runs using GitHub Actions concurrency controls.

---

# 27. Generated Commits

Successful generation runs may commit:

- world-state changes;
- new batches;
- manifest updates;
- account updates.

Use a recognizable bot commit message such as:

```text
chore(feed): generate synthetic feed <run-id>
```

Avoid workflow recursion.

A generated-data commit should not cause another AI generation cycle.

---

# 28. GitHub Pages Compatibility

The production build must work correctly when deployed beneath a GitHub Pages repository path rather than assuming `/` is always the site root.

Avoid server-dependent application routes.

If routing becomes necessary, use an approach compatible with static GitHub Pages hosting.

The first version should ideally remain a single-page feed.

---

# 29. Transparency

The interface must clearly indicate that the network is synthetic.

Use a visible but unobtrusive message such as:

> Everything here is AI-generated. None of these people are real.

Do not design the site to deceive visitors into believing these are genuine social-media posts.

Account profiles are fictional.

Events presented as part of the synthetic universe should not fabricate claims about real private individuals.

---

# 30. Safety Boundaries

The synthetic internet may contain:

- disagreement;
- sarcasm;
- mild profanity;
- awkward opinions;
- fictional drama;
- arguments;
- intentionally annoying personalities.

This variation is useful for realism.

However, generation should avoid:

- doxxing;
- real personal data;
- targeted harassment of real people;
- credible impersonation of real individuals;
- explicit sexual content;
- extremist recruitment or praise;
- actionable violent wrongdoing;
- dangerous instructional content.

The objective is a compelling fictional internet, not an unmoderated harmful-content generator.

---

# 31. Observability

A generation run should emit useful GitHub Actions logs including:

- run ID;
- generation attempt number;
- HTTP success/failure;
- validation success/failure;
- broad validation error reason;
- model ultimately returned by OpenRouter when available;
- number of generated posts;
- number of generated comments;
- total resulting batches;
- whether publication succeeded.

Never log the API key.

Avoid logging huge complete prompts/responses by default.

Failures should be understandable from Action logs.

---

# 32. Local Development

Provide straightforward commands for:

```text
install
run frontend locally
typecheck
test
build
generate feed locally
```

Local feed generation should use `OPENROUTER_API_KEY` from the environment.

The application should include checked-in seed/sample data so frontend development does not require making an OpenRouter call.

# 33. Prompt Management

AI prompts must exist as version-controlled files rather than giant strings buried inside TypeScript.

At minimum maintain prompts for:

```text
bootstrap world
advance world
```

Prompt construction may combine:

- prompt template;
- relevant world state;
- active storylines;
- account information;
- summaries of recent activity;
- generation constraints.

Prompt versions should be easy to inspect and modify.

---

# 34. Future Analytics Compatibility

Do not implement an analytics backend in V1.

However, avoid architectural choices that would prevent later feedback signals from influencing generation.

A future version may collect signals such as:

```text
scroll depth
dwell time
posts opened
comments expanded
likes/dislikes
topic affinity
author affinity
abandonment
```

These signals may eventually be summarized and supplied to the generator during the next three-hour cycle.

The conceptual future loop is:

```text
synthetic world
      │
      ▼
generated feed
      │
      ▼
human behavior
      │
      ▼
analytics summary
      │
      ▼
next generation cycle
      │
      ▼
evolving synthetic world
```

Do not build this backend yet.

# 36. Engineering Philosophy

Prefer:

```text
simple
observable
validated
replaceable
boring infrastructure
interesting product behavior
```

over:

```text
distributed systems
premature abstraction
backend services
complex event pipelines
microservices
unnecessary cloud infrastructure
```

The interesting engineering problem is **the synthetic world**, not hosting.

GitHub Pages + GitHub Actions + static JSON is intentionally sufficient for V1.

# 37. Definition of Done — V1

V1 is complete when all of the following are true:

1. The site is deployed successfully on GitHub Pages.

2. Opening the site immediately displays a polished synthetic social feed.

3. At least approximately 30 persistent fictional accounts exist.

4. Accounts maintain stable names, personalities, and writing characteristics between generation runs.

5. The feed contains multiple content styles and discussions.

6. Posts reference prior synthetic events or users often enough to demonstrate world continuity.

7. The feed loads newer and older immutable JSON batches incrementally.

8. GitHub Actions automatically generates a new feed batch approximately every three hours.

9. The generation workflow can also be manually triggered.

10. OpenRouter uses:

```text
openrouter/free
```

11. The OpenRouter key exists only as:

```text
OPENROUTER_API_KEY
```

in secure runtime configuration/GitHub Actions secrets.

12. Invalid or malformed AI output is detected.

13. Retry logic handles transient OpenRouter and malformed-response failures.

14. Failed generation attempts cannot corrupt the previous valid world state or live feed.

15. The complete project passes type checking, tests, and a production build.

16. The UI clearly communicates that all content and people are synthetic.

17. No backend/database/authentication system is required.

18. A visitor can continuously scroll enough synthetic content to meaningfully judge whether the concept is compelling.

# 39. Final Product Standard

The project should not merely demonstrate that an LLM can produce JSON.

A successful result should create the sensation that:

> Something has been happening here while I was gone.

When a visitor returns hours or days later, the feed should contain new activity involving recognizable synthetic people and ongoing synthetic events.

That continuity is the core differentiator of Dopamine Feed.
